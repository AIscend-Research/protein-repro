# Paper writing guide

Everything needed to write the MLRC paper, section by section: which numbers to
use, which file each one comes from, which figure goes where, and what can and
cannot be claimed. All experimental work (roadmap Phases 1–4) is complete; this
document exists so the write-up doesn't require re-deriving anything.

**Rule for the whole paper: no number gets typed by hand.** Every table in the
paper is regenerated by `reproduction/make_paper_tables.py` into
`reproduction/paper_tables.md`, and every table there names the CSV it came
from. Copy from `paper_tables.md`, not from prose in READMEs.

---

## 0. Do this before writing (~5 minutes)

Two of the twelve paper tables are currently prose-only in a README. Running the
two committed scripts backfills them so the whole paper sits on the same
auto-generated footing:

```bash
bash reproduction/phase3_extensions/low_resource/run_low_resource.sh
python reproduction/phase3_extensions/low_resource/analyze_low_resource.py

bash reproduction/phase3_extensions/failure_cases/run_failure_cases.sh

python reproduction/make_paper_tables.py   # -> 12/12 tables
```

Until then `paper_tables.md` reports 10/12 and marks the other two as missing
rather than faking them. The underlying numbers already exist in the Phase 3
README (§2c and §3c) if you would rather cite those and skip the re-run — but
then say so, because those two tables won't be machine-traceable like the rest.

## 2. Section-by-section

### Introduction / motivation

Frame around the honest reproduction target: the paper's headline claims include
wet-lab validation that a student team cannot reproduce, so the target is the
**computational design pipeline** — install, run pretrained inference, score,
stress-test. Say this explicitly and early; it is a strength of the write-up,
not a caveat to bury.

The accessibility angle is the throughline: 1.66M parameters, 6.7 MB checkpoint,
runs on a laptop CPU. The extensions all test whether that accessibility holds up
under conditions a small lab actually faces (noisy structures, missing density,
no GPU, imperfectly-curated PDB files).

### Method reproduction

- Model: `v_48_020` for **both** full-backbone and CA-only, deliberately, so the
  comparison isn't confounded by different training-noise levels (the CA weights
  ship in three noise variants). Say this — it's a real methodological choice.
- Checkpoints: full-backbone `vanilla_model_weights/v_48_020.pt` (1.66M params),
  CA-only `ca_model_weights/v_48_020.pt` (1.65M).
- Parsing: the repo's own `helper_scripts/parse_multiple_chains.py` and
  `assign_fixed_chains.py`. **No custom PDB parser was written** — worth stating,
  since divergent parsing is a common reproduction failure mode.
- Phase 0 smoke test reproduced the official example exactly (5L33: score 0.8576,
  recovery 38.7%), with matching git hash and seed.
- Seed 37 throughout; 8 sequences per backbone per temperature; batch_size 1.
- Exact commands: `phase2_reproduction/README.md`, or `reproduction/run_all.sh`
  for the whole pipeline in dependency order.

**Deviations from the official README to disclose** (all in
`phase2_reproduction/README.md` §Deviations):
1. `--sampling_temp "0.1 0.2 0.3"` in one invocation rather than three runs.
2. `--num_seq_per_target 8` instead of the examples' 2, for stabler per-protein means.
3. `--ca_only` with `--jsonl_path` rather than `--pdb_path` — verified equivalent
   via `tied_featurize` (`protein_mpnn_utils.py:197`), not a hack.

### Dataset

30 structures from RCSB, `inputs/phase1_dataset/pdbs/`, 36–585 resolved residues:

```
1AKI 1BPI 1CRN 1CSP 1ENH 1FKB 1HEL 1IGD 1LZ1 1MBN 1PIN 1R69 1RIS 1SHG 1STN
1TIM 1TUP 1UBI 1UBQ 1VII 2ACY 2CI2 2CRO 2GB1 2LZM 2PCY 2PTL 3CHY 3PGK 4HHB
```

21 clean / 9 stress-test; 27 monomers / 3 multimers.

**Two dataset caveats that must appear in the paper, not be quietly dropped:**
1. **Only 28 unique sequences, not 30** — 1AKI/1HEL are both hen lysozyme and
   1UBI/1UBQ are both ubiquitin. Independent RCSB depositions picked
   independently while curating classic small structures. Left as-is rather than
   re-curated after the Phase 2 runs (which would have invalidated them).
2. **1TIM was reclassified clean → stress-test on self-audit.** Its 1981
   deposition has no REMARK 465 records at all, so the REMARK-based missing-residue
   count said 0 while the structure actually skips residue 3 in both chains. The
   official parser's own `-` gap placeholders turned out to be the more reliable
   signal than REMARK 465, and `build_summary.py` now uses that as authoritative.
   This is a good, concrete reproducibility anecdote — it shows metadata you'd
   naively trust can be silently absent.

Also worth a sentence: **1TUP required explicit chain restriction.** The official
parser has no concept of nucleic acid chains and parsed p53's two 21-nt DNA
chains as designable protein, inflating the reported length from 585 to 627.
Without `assign_fixed_chains.py --chain_list "A B C"` the pipeline would silently
redesign DNA as amino acids. That's a real usability trap for anyone pulling
multi-chain structures from RCSB.

### Reproduction results

Headline (T=0.1, 30 proteins, 240 samples per model per temperature):

| model | recovery | NLL | perplexity |
|---|---|---|---|
| full-backbone | 46.4% | 0.866 | 2.397 |
| CA-only | 41.3% | 0.953 | 2.623 |

**What reproduced qualitatively:**
1. Full-backbone beats CA-only at every temperature (+5.1 pp at T=0.1) — the
   paper's claim that N/C/O context improves design accuracy.
2. Recovery falls and perplexity rises monotonically with temperature for both
   models — the expected diversity/accuracy tradeoff.
3. 0/30 failure rate for both models, including the 9 stress-test structures and
   the 1TUP DNA complex under chain restriction.

**What did not match numerically, and why:** absolute recovery (~40–46%) is below
the paper's ~52%. Attribute this to dataset mismatch, not implementation error —
our 30 hand-curated structures are not the paper's held-out CATH-clustered test
split, which isn't separately downloadable (the 16.5 GB training tarball is the
only source of `test_clusters.txt`, see `training/README.md`), and our set skews
toward short simple domains (1CRN at 46 residues). State the gap plainly and give
the reason; don't explain it away.

Perplexity is `exp(score)`, where score is mean per-residue NLL in nats —
confirmed against the `.npz` score files in Phases 0/1.

Runtime: full-backbone 720 sequences in 281.9 s (153.2 seqs/min, 9.40 s/protein);
CA-only 262.6 s (164.5 seqs/min, ~7% faster, consistent with a smaller
per-residue feature tensor). CPU only — see the MPS finding below.

Peak memory: 862 MB RSS on the largest structure (1TUP, 627 res).

**The clean-vs-stress-test comparison is a negative result — report it as one.**
Full-backbone loses ~2 pp on stress-test structures (expected direction) but
CA-only *gains* ~2 pp (wrong direction). Two identifiable reasons:
(i) ProteinMPNN's own score/recovery are computed only over resolved positions
(`_scores()`, `protein_mpnn_utils.py:39`), so missing residues elsewhere don't
penalize the positions being evaluated; (ii) the split confounds completeness
with protein identity — 21 vs. 9 *different* proteins. The roadmap's expected
"behavior changes predictably with input completeness" does **not** hold on this
natural-subset comparison, and the controlled test of that claim is the Phase 4
masking experiment. Saying this clearly is better than quietly leaning on the
masking result instead.

### Extensions

**Coordinate noise (Fig 4) — the single most interesting result.**

| noise (Å) | full-backbone | CA-only |
|---|---|---|
| 0.0 | 46.5% | 40.5% |
| 0.1 | 45.6% | 40.1% |
| 0.2 | 43.5% | 38.0% |
| 0.3 | 39.5% | 35.1% |
| 0.5 | 23.9% | 25.4% |

The models **cross over between 0.3 and 0.5 Å**. Full-backbone is more accurate
on clean structures but degrades faster; its extra N/C/O geometric detail is more
fragile under coordinate corruption than CA-only's sparser representation. Lead
the extensions section with this — it is a genuinely new, actionable finding not
in the original paper: with low-resolution or imprecise coordinates, the *weaker*
model is the better choice.

**Residue masking (Fig 5) — the contrast that makes the noise result meaningful.**

| mask % | full-backbone | CA-only |
|---|---|---|
| 0 | 47.1% | 40.1% |
| 10 | 44.3% | 36.3% |
| 20 | 38.5% | 30.8% |
| 30 | 33.6% | 26.5% |

No crossover; full-backbone keeps its lead throughout. Combined takeaway: noisy
structural context and *missing* structural context are different failure modes
with different relative impact on the two architectures. Prefer CA-only for noisy
coordinates, full-backbone for gapped density.

Methodological point to state: masking uses the exact `-`/NaN convention the
official parser uses for genuinely missing residues (verified against 1TIM's real
gap), and recovery is computed by the pipeline's own `mask_for_loss` over
**non-masked positions only** — so this measures designing the still-visible
structure with less context, not guessing the hidden region.

**Low-resource inference.**
- **MPS doesn't work at all**, and this is a finding rather than a limitation.
  The official device selection (`protein_mpnn_run.py:68`) only checks
  `torch.cuda.is_available()`. A patched copy adding an MPS branch crashes in
  `gather_nodes`/`gather_edges` (`protein_mpnn_utils.py:595-608`): Metal's
  `GatherND` kernel can't handle the 4D gather used for the k=48 nearest-neighbor
  graph. That's every forward pass, not an edge case. So "CPU vs. GPU on Apple
  Silicon" has the honest answer: there is no GPU path.
- Model size: 1.66M / 1.65M params, 6.68 / 6.62 MB.
- `num_seq_per_target` 8 → 1 gives ~7.3× speedup for 8× fewer sequences —
  sub-linear because the encoder forward pass is shared across samples. No
  accuracy cost, just fewer sequences.
- **Larger batch is faster on CPU, counter to intuition**: batch_size 8 runs the
  5-protein subset in 2.94 s vs. 5.08 s at batch_size 1, but uses 2258 MB vs.
  641 MB peak RSS (~3.5×). So `batch_size=1` is right when *memory* binds, not
  when speed does — a sharper statement than "use small batches on weak hardware."

**Generalization.** Recovery peaks at medium length (70–150 aa: 49.0% / 41.9%)
and dips for >150 aa (41.1% / 39.7%). Monomers beat multimers by 8.3 pp
(full-backbone), **but n=3 multimers** — report it, refuse to conclude from it.

Burial: buried 42.2% vs. exposed 33.3% (full-backbone), consistent with core
packing constraining sequence identity more than solvent-exposed positions.
**Disclose the substitution**: this uses a CA–CA contact-number proxy (neighbors
within 10 Å, excluding |i−j|<3), not DSSP solvent accessibility, because `mkdssp`
has no osx-arm64 build available via conda or Homebrew. Computed on 5
representative monomers, tertile split per protein.

**Failure cases — 4 of 6 fail in ways a user wouldn't want.**

| case | behavior |
|---|---|
| Malformed coordinate field | Hard crash, unhandled `ValueError` in `parse_PDB_biounits` — kills the *entire batch* parse, not just the bad file |
| Unusual residue code (`ZZZ`) | Silently becomes a gap `-`, no warning |
| Chain-ID collision | Silently collapses; colliding (chain, resnum) keys overwrite in the parser's dict, residues lost |
| `--max_length` exceeded | Graceful discard with an explicit message — the one well-behaved path |
| `--backbone_noise 5.0` | No crash, but degenerate: sequences collapse to one repeated residue, ~3% recovery, *below* random guessing |
| 3386-residue synthetic structure | Succeeds — 24.5 s, 2.03 GB, no degradation |

The framing that matters: three of these fail **silently**. The pipeline
"succeeds" and emits a FASTA that is garbage or quietly truncated. Anyone running
this on real-world, imperfectly-curated PDB files should validate inputs before
the run, because the pipeline won't catch most of this. That's the responsible-
modeling payoff of the whole section.

**ESMFold structure validation — the strongest single result.**

| protein | designed pLDDT | native pLDDT | CA RMSD (Å) | recovery |
|---|---|---|---|---|
| 1UBQ | 92.8 | 90.5 | 0.79 | 55.3% |
| 1VII | 69.9 | 92.1 | 2.59 | 22.2% |
| 2GB1 | 83.1 | 88.3 | 1.00 | 32.1% |
| 1CRN | 88.7 | 50.4 | 8.08 | 58.7% |
| 1ENH | 88.8 | 91.2 | 0.64 | 40.7% |

3 of 5 designs fold with high confidence and ≤1.0 Å CA RMSD to native at only
32–55% sequence identity. **This validates the paper's actual claim** — that
designs reproduce the target *fold*, not the native sequence — which sequence
recovery alone cannot do. Give it real space despite n=5.

1VII is a consistent weak case (lowest pLDDT, highest RMSD, lowest recovery).
**Do not over-read 1CRN**: ESMFold is only 50.4 pLDDT confident about the
*native* crambin fold, the QCP superposition logged a convergence warning, and
the 8.08 Å likely reflects ESMFold's own uncertainty rather than design failure.

Also report the platform finding: Kaggle assigned a P100 (compute capability 6.0)
whose capability its own pre-installed PyTorch build doesn't support, and the
crash only surfaces on the first real forward pass, not at `.cuda()`. Six
push/debug iterations to work around. Even "free GPU" platforms have non-obvious
compatibility gaps — squarely on-theme for accessibility.

### Limitations

1. 30 structures / 28 unique sequences, hand-curated, not the paper's CATH test split.
2. No wet-lab validation; ESMFold on n=5 is the only structural check.
3. Buried/exposed uses a contact-number proxy, not DSSP.
4. n=3 multimers — the monomer/multimer gap is reported but not concluded from.
5. CPU-only throughout; no CUDA GPU was available, and MPS is unusable.
6. Absolute recovery is below the paper's, attributed to dataset mismatch — we
   could not rule this out directly, since the paper's test split isn't
   separately downloadable.

### Conclusion — the three-way split

- **Reproduced**: full-backbone > CA-only; monotonic temperature/recovery
  tradeoff; the pipeline installs and runs on laptop-class CPU hardware with a 0%
  failure rate on curated inputs; designs fold to the target structure (ESMFold).
- **Did not reproduce numerically**: absolute recovery (~46% vs. ~52%), explained
  by dataset mismatch rather than implementation divergence.
- **New / beyond the original paper**: the noise-robustness crossover between the
  two model variants; the noise-vs-masking asymmetry; four of six edge cases
  failing silently; MPS being entirely unusable; larger batches being faster but
  memory-hungrier on CPU.

## 4. Things not to claim

- Any wet-lab success rate. None was performed.
- That the monomer/multimer gap is real — n=3.
- That buried/exposed numbers are DSSP-based — they are a geometric proxy.
- That ProteinMPNN "fails on incomplete structures" based on the clean/stress-test
  split — that comparison is confounded and points the wrong way for CA-only; the
  masking sweep is the controlled evidence.
- That the ~46% vs. ~52% gap is an implementation bug — it's most likely dataset
  mismatch, but we could not verify that directly, so say "most likely," not "is."
